# MovieHub — лабораторные работы по веб-программированию

Единый портал о кино: Django 5.2 (Python), шаблоны HTML, CSS и TypeScript/Vite. Каждая лабораторная расширяет проект. С №4 сервер работает на Django, а готовый интерфейс предыдущих работ сохранён.

## Запуск

Требуются Python 3.11+ и Node.js 22.12+. Для поиска фильмов создайте локальный `.env` по образцу `.env.example` и укажите `OMDB_API_KEY`. Ключ можно получить на [сайте OMDb](https://www.omdbapi.com/apikey.aspx) и активировать по ссылке из письма. После изменения `.env` перезапустите сервер. Не добавляйте ключ в `VITE_*`, Git или экспорт Postman.

```bash
npm ci
npm run setup
npm run dev
```

Откройте [localhost:5173](http://localhost:5173). `dev` собирает фронтенд, применяет миграции и запускает Django + пересборку Vite при изменении CSS/TS. После изменения фронтенда обновите страницу (HMR не используется). HTML отдаёт Django, отдельного Express/Vite-сервера больше нет. SQLite хранится в игнорируемом `data/moviehub.db`.

Для запуска собранной версии:

```bash
npm run build
npm run migrate
.venv/bin/python manage.py collectstatic --noinput
npm start
```

Адрес тот же: `http://127.0.0.1:5173`. `start` использует Gunicorn. Это локальные настройки; облачный запуск описан ниже.

## Страницы

- `index.html` — главная страница, слайд-шоу и видео.
- `movies.html` — поиск реальных фильмов OMDb, фильтр по году, страницы результатов и учебные жанровые блоки.
- `movie.html?id=tt0816692` — подробная карточка фильма из OMDb.
- `about.html` — информация о портале и учебные примеры.
- `auth.html` — формы входа и регистрации с клиентской и серверной валидацией.
- `profile.html` — защищённый личный кабинет и выход из аккаунта.

### API авторизации

| Метод и путь | Назначение |
| --- | --- |
| `POST /api/auth/register` | Создать аккаунт и сессию |
| `POST /api/auth/login` | Войти по email и паролю |
| `GET /api/auth/me` | Получить текущего пользователя |
| `POST /api/auth/logout` | Завершить текущую сессию |
| `GET /api/health` | Проверить работу сервера |
| `GET /api/auth/csrf` | Получить CSRF-токен и cookie перед POST-запросом |

JSON-поля и прежние адреса сохранены. Для POST из Postman сначала вызовите `/api/auth/csrf`, сохраните cookie и передайте `csrfToken` в заголовке `X-CSRFToken`. В браузере это делает `src/csrf.ts`. Без токена/с доверенным токеном, но чужим Origin, ответ — `403`.

### Перенос существующей базы

Перед первым `migrate` остановите старый сервер и сделайте резервную копию SQLite, например `sqlite3 data/moviehub.db '.backup data/moviehub-before-lab04.db'` (не повторяйте команду поверх нужной резервной копии).

Миграция `0002_import_legacy` один раз копирует `users`/`sessions` в `portal_account`/`portal_loginsession`. Исходные таблицы остаются нетронутыми. ID, поля, хеши и сроки сессий сохраняются. Повторный `migrate` ничего не копирует. Не запускайте Express после переноса: новые данные записываются только в Django-таблицы. Для возврата к старой версии понадобится резервная копия; миграция намеренно необратима.

Новые пароли хешируются Django, старые bcrypt-пароли обновляются после успешного входа. Исходная cookie `moviehub_session` совместима. Тесты используют отдельную временную базу, не реальные аккаунты.

### Replit: запуск в облачной рабочей среде

1. Войдите в [Replit](https://replit.com/) и импортируйте [репозиторий GitHub](https://github.com/Rokki0710/web-labs) через Import from GitHub. Не поручайте генератору переписывать проект.
2. В **Secrets** добавьте `DJANGO_SECRET_KEY` (случайная строка, минимум 50 символов) и `OMDB_API_KEY`. Ключи не вводите в код, чат Replit Agent или `.replit`.
3. `.replit` задаёт Python/Node, `DJANGO_DEBUG=false`, доверенный HTTPS-прокси и порт 3000. Точные домены берутся из `REPLIT_DEV_DOMAIN`/`REPLIT_DOMAINS`. Если платформа их не предоставила, задайте `DJANGO_ALLOWED_HOSTS` (домен без схемы) и `DJANGO_CSRF_TRUSTED_ORIGINS` (`https://домен`). Не используйте `*`.
4. Нажмите **Run**. Команды установят зависимости, соберут фронтенд, соберут статику, применят миграции и запустят Gunicorn. В Preview откройте выданный HTTPS-адрес.
5. Проверьте `/api/health`, каталог, регистрацию, профиль, выход и повторный вход. В Postman поменяйте `baseUrl` на этот адрес и запустите папку MovieHub. Только после этого облачная часть ТЗ проверена.

В облаке создаётся **новая** база: реальные локальные аккаунты/база не публикуются и не загружаются автоматически. SQLite подходит для учебного запуска в рабочей среде. Для **Publish / Autoscale** нужна постоянная PostgreSQL-база: подключите её в Replit, передайте `DATABASE_URL` через Secrets. Django поддерживает её через `dj-database-url` и `psycopg`; локальный SQLite не переносится в неё автоматически. Не храните аккаунты в эфемерном файловом хранилище опубликованного приложения. Платные ресурсы не включайте без отдельного решения.

Продакшен: `DJANGO_DEBUG=false`, уникальный `DJANGO_SECRET_KEY`, точные hosts/origins, HTTPS. `DJANGO_TRUST_PROXY=true` только за доверенным прокси, который перезаписывает X-Forwarded-Proto. Cookie Secure и HTTPS redirect включены автоматически. Проверка: `.venv/bin/python manage.py check --deploy` с этими переменными.

Кэш/rate limiting в памяти рассчитаны на один процесс (Gunicorn workers=1); за прокси ограничение может быть общим для посетителей. Для масштабирования понадобятся общий кэш и настройка доверенных IP. PostgreSQL и реальный Replit-запуск проверяются отдельно, локальные тесты их не заменяют.

При Publish отдельно проверьте Secrets в Publishing: настройки рабочей среды не гарантируют их наличие в опубликованном приложении.

Источники настроек: [Django deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/), [конфигурация Replit](https://docs.replit.com/features/project-setup/configuration), [хранилище и Secrets при публикации](https://docs.replit.com/build/troubleshooting).

## Лабораторная №5 — база данных

Функциональность уже реализована в №2/№4 и сохранена без дублирования моделей или пустых миграций. В №5 добавлены пять проверок БД в `portal/tests/test_database.py` и выполнена регистрация через браузер на отдельной временной SQLite.

| Пункт ТЗ | Где выполнен / как проверен |
| --- | --- |
| Создать и подключить БД | SQLite `data/moviehub.db`, `DATABASES` в `config/settings.py`, Django ORM |
| Пользователь из формы регистрации | `auth.html` → `src/auth.ts` → `POST /api/auth/register` → `RegisterForm` → `Account`; SQL-проверка всех сохранённых полей и открытие профиля |
| Защита пароля | `make_password`/`check_password`: PBKDF2-SHA256, отдельная случайная соль; одинаковые пароли дают разные хеши, неверный пароль не проходит |
| Дополнительные модели | Уже есть `LoginSession` с `ForeignKey(Account)`; хранит SHA-256 токена, срок действия и время создания |
| Миграции | `0001_initial` создаёт модели/ограничения, `0002_import_legacy` переносит старые данные; обе применены, новых изменений схемы нет |
| Целостность | Уникальный email без учёта регистра, возраст 14–100, внешняя связь и каскадное удаление сессий через ORM проверены тестами |

Точнее говорить **хеширование**, а не обратимое шифрование пароля. Пароль не расшифровывается: Django проверяет введённое значение через `check_password`. Алгоритм, число итераций, соль и результат хеширования хранятся в `password_hash`. Хеши, пароли и токены не возвращаются в JSON профиля. Старые bcrypt-пароли совместимы и обновляются после входа. См. [официальную документацию Django](https://docs.djangoproject.com/en/5.2/topics/auth/passwords/).

`Account` — собственная ORM-модель текущей системы авторизации, не подмена `AUTH_USER_MODEL` и не `django.contrib.auth.User`. Менять рабочую систему и переносить данные ещё раз для этого ТЗ не требуется. Профильные поля уже входят в Account, отдельная дублирующая модель Profile не нужна.

### Демонстрация преподавателю

1. Выполнить `npm run dev`, открыть `/auth.html#register` и зарегистрировать отдельный учебный аккаунт с вымышленными данными и новым паролем (не личным).
2. Показать переход в профиль с введёнными полями. Выйти и войти снова с тем же email/паролем — данные читаются из БД.
3. Показать модели и миграции, затем выполнить проверки:

```bash
.venv/bin/python manage.py showmigrations portal
.venv/bin/python manage.py migrate --check
.venv/bin/python manage.py makemigrations --check --dry-run
.venv/bin/python manage.py test portal.tests.test_database
```

4. Для демонстрации SQL без вывода персональных данных и хешей открыть `sqlite3 data/moviehub.db` и выполнить:

```sql
SELECT COUNT(*) AS accounts FROM portal_account;
SELECT COUNT(*) AS sessions FROM portal_loginsession;
SELECT COUNT(*) AS orphan_sessions
FROM portal_loginsession AS s
LEFT JOIN portal_account AS a ON a.id = s.user_id
WHERE a.id IS NULL;
```

Тесты работают в отдельной тестовой БД и автоматически откатывают свои данные. В браузерной проверке №5 использовался отдельный сервер с временной SQLite; существующие пользовательские аккаунты не изменялись. Общий набор — 23 теста (`npm run check`).

Облачный запуск из №4 остаётся отдельным незавершённым этапом: подключение локальной SQLite не означает, что Replit уже запущен. PostgreSQL через `DATABASE_URL` предусмотрена, но настоящая облачная БД пока не проверена.
